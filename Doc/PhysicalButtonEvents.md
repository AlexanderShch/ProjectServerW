# События контроллера

При обработке физических СТАРТ и СТОП контроллер сохраняет событие перед изменением режима. Серверные команды, автостарт и автоматическая остановка событий кнопок не создают. Импульс короче периода опроса может пройти между двумя чтениями входа IO.

В RAM помещается 16 неподтверждённых событий. Диагностика занимает максимум 12, кнопки могут занять все 16. При заполнении новые записи соответствующей категории учитываются отдельным накопительным счётчиком потерь. Перезагрузка контроллера очищает RAM.

При первом отказе запроса датчика сохраняются его адрес, функция, причина, ожидаемая и принятая длина, время, код UART и до девяти фактически принятых байтов. Исправный ответ завершает серию ошибок и формирует событие восстановления с длительностью и количеством неудачных попыток. Для IO чтения DI, DO и запись выходов учитываются раздельно. Команда GET_SENSOR_DIAG предоставляет минутную статистику попыток; сервер автоматически использует её только со старой прошивкой без расширенного флага событий.

Контроллер опрашивает датчики и модуль ввода-вывода по Modbus RTU через UART5. Для каждого запроса ожидаемую длину вычисляют по функции и числу запрошенных регистров или битов. Обычно это 9 байт для двух регистров, 7 для одного регистра или 16 дискретных входов или выходов, 8 для подтверждения записи и 5 для ответа с исключением Modbus.
До обновления показаний контроллер проверяет состояние UART и факт приёма, границы кадра, адрес, функцию и соответствие фактической длины запросу. Для чтения проверяется ByteCount, затем CRC по фактически принятому кадру. Ответ с исключением проверяется отдельно по длине и CRC. При ошибке чтения контроллер удерживает предыдущие показания.
После трёх подряд ошибок приёма активный датчик переходит в Active=0. Контроллер продолжает пробные опросы. Неудачные опросы неактивного устройства не увеличивают счётчики ошибок, не попадают в минутную сводку и не создают события. Первый правильный ответ снова включает устройство. Если до отключения была открыта серия сбоев, правильный ответ завершает её событием восстановления. UseInDefrost управляет участием в регулировании независимо от активности на шине.

## Формат обмена

Все многобайтовые числа little-endian. Команда SEND_STATE с одним байтом 01 запрашивает расширение. После обычных 60 байтов телеметрии новый контроллер добавляет байт флагов. Бит 0 означает наличие событий. SEND_STATE без параметра возвращает прежние 60 байтов.

- GET_EVENT (0D), запрос 16 байтов с кандидатом на идентификатор сессии. Первое чтение закрепляет идентификатор до перезагрузки. Ответ содержит идентификатор (16), потери кнопок (4), потери диагностики (4), текущий размер очереди (1). При непустой очереди далее идут номер (4), время от запуска в секундах (4) и тип (1). Типы 1 и 2 обозначают СТАРТ и СТОП, 3 и 4 — сбой и восстановление. Для типов 3 и 4 следуют 27 байтов SensorEventDetail. Максимальная длина данных ответа — 61 байт.
- ACK_EVENT (0E), запрос содержит идентификатор (16) и номер (4). Подтверждение удаляет только выданную головную запись. Потерянный ответ или подтверждение допускают повторное чтение и повторный ACK.
- Сервер записывает событие в log.txt, выполняет Flush(true), затем подтверждает его. Ключ из идентификатора и номера защищает от повторной записи, в том числе после перезапуска сервера. После подтверждения сервер уступает канал телеметрии. Следующее событие читается только после новой телеметрии с установленным флагом, даже если в очереди осталось несколько записей.
- Со старой прошивкой сервер опрашивает GET_BUTTON_EVENTS раз в 30 секунд. Ответ INVALID_CODE отключает этот опрос до перезапуска или нового соединения. Старый сервер читает кнопки из общей очереди прежними командами 0B/0C. Его подтверждение оставляет диагностические записи в очереди.

Проверки очереди и серверного журнала выполняет `python tests/Run-ButtonEventTests.py` из среды vcvars64.

## Согласование с телеметрией и параметрами (4.0.0)

Запрос событий не отправляется, пока строка телеметрии ждёт лог ПИД, идёт инициализация или занят конвейер команд. После SEND_STATE запрос событий также откладывается до приёма телеметрии либо истечения секунды ожидания. Диагностические ответы не поступают в очередь ответов таблиц параметров.

Уже отправленный диагностический запрос занимает канал до проверенного ответа либо таймаута 1 с. Ожидание освобождается сетевым потоком без участия UI; обычная команда параметров ждёт освобождения канала. Для группы 7 это ожидание входит в общий бюджет 950 мс: при исчерпании бюджета попытка чтения пропускается. Отложенные диагностические ответы повторно проверяются по идентификатору соединения перед обработкой в UI.

Проверки совместной работы с параметрами, повреждённого ответа и ограниченного ожидания выполняет `tests/Run-LogSessionIsolationTests.ps1` с локальным имитатором контроллера.

## Обмен версии 4.0.0 с идентификатором запроса и отдельным GET_PROCESS_LOG

Текущий сервер требует этот формат уже для первого GET_VERSION. Перехода на старый формат без идентификаторов нет: сервер и прошивку следует обновлять вместе. Версии сервера и контроллера — 4.0.0.

Каждый новый запрос получает ненулевой 64-битный requestId: счётчик начинается со случайного значения для экземпляра формы и увеличивается, в том числе после переподключения. DATA_OK/DATA_FALSE используют ID подтверждаемого SEND_STATE. CRC покрывает и идентификатор. Формат команды: `[Type|0x80][Code][DataLen+8][requestId uint64 LE][Data][CRC16]`. Ответ: `[AA 55][Type|0x80][Code][Status][DataLen+8][requestId uint64 LE][Data][CRC16]`. Размер максимального ответа с параметрами процесса: 127 байт внутреннего кадра, 129 байт с AA 55. Элемент очереди и буфер UART контроллера увеличены до 132 байт.

Инициатор — сервер; одновременно выполняется один запрос. Проверяются соединение, requestId, тип, код, стадия; для параметров — группа/страница. Ответ с прошлым ID отбрасывается даже при полностью одинаковом коде повторного запроса. Таймауты и отбрасывания журналируются с ID. Инициализация и установка параметров имеют приоритет, затем опрос телеметрии и параметров процесса, затем события диагностики.

SEND_STATE возвращает только телеметрию. В расширенном байте бит 0 означает наличие событий, бит 1 — наличие снимка параметров работающего автоматического алгоритма. Контроллер фиксирует этот признак по DefrostControl_IsEnabled, а не по состоянию ТЭНов. DATA_OK подтверждает телеметрию и не вызывает второго ответа.

При бите 1 сервер отправляет GET_PROCESS_LOG (REQUEST 03, Code 0F) с собственным новым requestId. Данные команды — 8-байтовый ID телеметрии, для которой нужны параметры. Контроллер возвращает сохранённый при этой телеметрии ControlLogPayload (113 байт) либо EXECUTION_ERROR при несовпадающем ID/отсутствующем снимке. Сервер дополняет соответствующую pendingRow в той же сессии WorkData. В простое запрос не отправляется. При таймауте строка телеметрии сохраняется без недополученных параметров; поздний ответ не переносится в другую строку.

Ожидание обычного ответа — 1000 мс, бюджет группы 7 — 950 мс. Проверки: tests/Run-LogSessionIsolationTests.ps1 (кодирование, максимальный кадр, повторная команда с другим ID, привязка строки) и tests/Run-ButtonEventTests.py (Modbus, очередь, журнал, отсутствие лога на DATA_OK и защита от старого ACK).
